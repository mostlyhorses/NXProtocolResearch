At startup the Camera requests state of each Lens property using the 1006 operation, unlike the 100C and 100D operations that query the 60xx Specific Data codes only once (the first time a new lens is seen).

My guess is this does a few things:

- Indicates the presence and state of switches on the lens
- Reports the current state of focus/zoom/aperture/ois/etc
- And there's something that is , maybe the values that can be set???

# Lens Response

It's not obvious what the data means, but by comparing responses from different lenses and the same lens in different startup configurations, some patterns can be observed and the functions guessed. The quote below is the initial notes, followed by a table with the current thoughts on its meaning.

> These all vary in length, and can even vary across lenses (but not often).
> 
> It appears that the start of the packet is the same as the 100C message, but only using data formats 0002 and 0004, so there is no 'number of elements' field.
> 
> There is no checksum, as some responses vary by only a single byte.
> 
> It seems that on many of the messages (not all) that the 11th byte (quite possibly bytes 10-11, e.g. 16-bit) is the number of bytes to follow. After this byte the values are often sequential, e.g. 0,1,2,3, or 0,1,0,2,0,3, or 0,1,10,11,20,21, but not always.
> 
> Message types 0x5007, 0x5008, and 0x5011 are the ones that have been observed responding to the 0x1007 opcode; and these (with the addition of 0x5009) are the ones that don't follow the previous observation about bytes 10-11. Perhaps 0x5009 hasn't been observed because it always actuates fast enough that the body doesn't need to query its current position.
> 
> The sequential patterns feel like flags, but I can't see the pattern. The byte are possibly divided into upper and lower nibbles as the upper 4-bits often repeat with the lower 4-bits varying, e.g. 0x10,11,20,21, but then some values repeat (0x00). Perhaps its mapping camera states to lens states. E.g the index represents a camera state, and the value is what can be done on the lens?
> 
> Actually, perhaps the sequential patterns are the permitted values that can be sent in an 0x1008 opcode, the upper nibble is the features and the lower nibble the value?  But 0x00 can appears in the list multiple times. The list isn't always pairs, can be 5 or 7 elements. Could the sequential patterns be a mapping from the cameras control to the lenses control:
> 
> - E.g. the camera has a list of potential controls, e.g. Feature 1 on, feature 1 off, feature 2 state 1, feature 2 state 2, feature 2 state 3, abort, etc.
> - The lens may or may not support this control
> - The lens may use a different code to represent that control.
> - This table maps the camera controls into the codes that have to be sent to the lens.
> - Take property 0x5001. The camera knows about 4 different communication modes: A/B/C/D. The list then maps them into the codes that need to be sent to the lens, and whether the lens supports it. E.g. If the body wants mode 'C' it has to send 0x02 to the 30mm, but 0x01 to the 60mm. 0x00 is like a 'safe' placeholder value when the lens doesn't support it.
> - To verify this, would have to find a way to make the body request a mode where the code for 2 different lenses differs and see if it lines up.
> 
> 0x5008 and 0x5009 are interesting because the data type is 0x0002 and the 11th byte is the number of zoom points or f-stops, an actual data value, rather than something describing framing of the packet. This would have to mean that if there is a generic framing/structure, that something preceding it in the packet identified it as a different layout - there doesn't appear to be.
> 
> The start of the messages is sometimes used to indicate the presence of a physical switch, and it's state.
> 
> ~~Without knowing more about what's being encoded, or having considerably more different examples, shouldn't put much weight onto arbitrary patterns that can be seen. Have to treat the data as following a general theme, but not a fixed structure. So decode each 50xx code independently.~~

## Targets and Current Values/States

It appears that things report a 'target' and a 'current' value. This would make sense if it can take the lens time to change from one state / value to another, or if the lens immediately reports its state after a set request:

For example:

- At startup the focus may move from it's initial position to a default position, and when this message is sent it is still in progress.
- When changing states it may take some time to get there, e.g. enabling OIS.

## State Mapping

This is the least understood part and is largely a guess based on one way of implementing something generic - but it doesn't feel very good.

~~Imagine you have a property of the lens that is adjustable and can take on certain values or states where:~~

- ~~Not every lens can support every state.~~
- ~~The value to send to the lens to put it in a particular state varies across lenses.~~
- ~~The lens knows about all the states the camera could ask for (it has to fill out so many entries in the mapping table).~~

&nbsp;

~~An example: Imagine a property of the lens called Foo. The camera body may in different situations want Foo to take on the values Off, Slow, Medium, Fast or Extreme, which are well defined values (everyone knows what a Slow Foo does compared to an Extreme Foo). Some lenses have a fine control of Foo and can set them to each of the values, and the values that need to be sent to the lens are 0x01, 0x02, 0x03, 0x04, and 0x05. Other lenses may only have Off and Medium, and the values to send to that lens are 0x01 and 0x02. So in this case we would have a table from lens 1 that looks like 0x01, 0x02, 0x03, 0x04, 0x05; but for the second lens it would look like 0x01, 0x00, 0x02, 0x00, 0x00. When the camera wants to set Foo to Slow on lens 1 it sees that it needs to send 0x02; but if it wants to set it on lens 2 it sees that it's not supported, but could choose either Off or Medium.~~

&nbsp;

Looking at the real data in the state mapping - it also appears the bytes are split into 4-bit nibbles, where the upper nibble is a group, and the lower nibble is a state. So for example on property 500D Operation Method Permission, some lenses have 4 groups and others just two; and some lenses spread their two groups out over the mappings where other lenses would have 4 groups.

&nbsp;

After looking at op1008, this idea about state mapping doesn't appear to hold. The state number sent in the Op1008 request for a property always comes from the state map; but it's the same across all lenses even if they have a different state number in the same entry. So perhaps when a lens doesn't support a state, the supported values just get spread out over the expected entries. 

&nbsp;

## Exceptions

The main exception to these tables that isn't understood is Property 0x5004 Focus Limit on the 50-150S lens. This identifies as type 0x00, but then the data looks more like type 0x01 or 0x10. Perhaps this special case is controlled by byte 6, which is zero in this  case.
