The first time a lens is observed by a camera it queries some constants from the lens. The camera initially uses the 0x100C operation to learn how much data is associated with each code, and then uses the 0x100D operation to get the data.

&nbsp;

# Support

All lenses

&nbsp;

# Camera Request

| Byte | Function | Example |
| --- | --- | --- |
| 0   | Packet Length | 0x05 |
| 1-2 | This Code | 0x10,0C |
| 3-4 | The 60xx Code | 0x60,03 |

&nbsp;

# Lens Response

These are all the same length. Checksum is the simple 8-bit sum of bytes 3..10

| Bytes |     |     |
| --- | --- | --- |
| 0   | The packet Length | 0x0C |
| 1-2 | Status | 0x20,01 |
| 3-4 | Data format | 0x40,04 |
| 5-8 | Number of elements | 0x00,00,00,02 |
| 9-10 | ?? Something to do with the 4008 data format | 0x00,00 |
| 11  | Checksum | 0x46 |

&nbsp;

Camera -> Lens : \[05 10 0C 60 03\] : Camera requests information about the info block 0x6003

Lens -> Camera: \[0C 20 01 40 04 00 00 00 02 00 00 46\] : Lens responds saying data format 0x4004, 2 elements, and checksum.

&nbsp;

# Notes

The camera requests 6003 (comms clock) first. Others are done in order except for 6019 which for some reason goes between 601B and 601C.

## Data Format

From the output of the 'st cap lens' command we can see how the number of data points relates to the data length for different formats. It also shows the values for the first 15 data points so we can see the number of bytes per value, and in some cases if signed values are present (only confirms, not denies it). Some of the numbering makes sense, int16, uint16, int32, uint32, but if the pattern holds then 4001 would have to be signed 8-bit, but we see values from 6-255 so it can't be, and 4002 goes to +144, so it can't be signed either - but don't know if the 'st cap lens' command is decoding it properly? It doesn't show the float values correctly, see note in table.

Looking at the type 4005 'st cap lens' output, this seems actually to be F32, but displayed multiplied by 10000 and rounded to integer.
